# 比赛与约球共用活动 ID

## 数据结构与唯一性

`activities.id` 是活动的统一 `BIGINT AUTO_INCREMENT` 主键。比赛、约球不再分别自增：`tournaments.id`、`match_posts.id` 使用分配到的活动 ID 作为各自主键。

- `activities.kind` 区分 `post` / `tournament`，保存时间与历史编号映射；不复制赛程、报名或详情大字段。
- 子表通过 `(id, activity_kind)` 复合外键引用统一主表，并分别要求类型固定为 `post`、`tournament`。主键、复合唯一约束和类型 CHECK 共同阻止编号重复、无主编号以及同一编号同时属于两种活动。
- MySQL 的类型列统一使用 `ascii_bin`，避免旧表字符集不同导致外键无法创建，并确保类型按大小写严格匹配。
- Redis `activity:id:allocate` 分布式锁限制取号并发入口，等待上限 5 秒，租约 30 秒，使用 Redis 库的持有者校验释放。锁超时、Redis 不可用或释放失败返回 503，由接口事务回滚，不降级为无锁取号。锁只覆盖取号操作，不代替数据库事务和约束。
- ID 由数据库自增序列生成，运行时不使用 `MAX(id)+1`。即使 Redis 租约失效，数据库仍拒绝重复主键。回滚或失败可以留下编号空缺；连续无空缺不是本次要求。
- 活动 ID 在现有小程序可精确表示的正整数范围内，超过 `2^53-1` 时拒绝分配或迁移，防止客户端数字精度造成错误映射。
- 正常取消/关闭活动不删除统一编号，禁止手动重置序列或复用历史活动编号。

两类报名记录继续存储在 `match_registrations`、`tournament_registrations`。各自的报名行 ID 是内部报名记录主键，允许数值相同；用户活动映射使用 `activity_id`，不能将报名行 ID 当作跨类型活动 ID。

## 查询与接口

- 现有比赛、约球接口返回的活动 `id` 即统一编号，并增加 `activity_id`。个人约球报名返回 `activity_id` / `post_id` 及独立报名行 `id`，比赛个人记录返回统一 `activity_id` / `id`。
- `/activities/{activity_id}` 按统一编号读取正确类型的详情。
- `/users/me/activities` 按当前用户查询两类报名摘要，使用 `UNION ALL`、稳定分页及确定的排序。不会把全部赛程和签表复制到个人记录中。现有独立详情和个人分页查询继续可用。
- 两类报名表增加 `(user_id, created_at, id)` 索引，活动及详情关联走主键，旧编号映射走 `(kind, legacy_id)` 唯一索引。真实 MySQL 查询计划及大数据性能仍需在隔离环境验收。

## 历史转换

迁移：`20261007_activity_ids`，前置 `20261007_post_history`。若旧比赛、旧约球拥有相同编号，**冲突双方都重新取号**；不冲突的历史编号保留。新编号从完整历史编号空间上界之后分配，避免旧别名与新编号混淆。

迁移保存 `(类型, 旧编号) → 新活动 ID`，更新约球报名、评论、比赛报名、订单、签表、操作记录及相应通知的外键/引用。旧 `/posts/{编号}`、`/tournaments/{编号}` 链接按类型解析旧映射。仅一个旧冲突数字不能区分两个活动；新统一详情接口只接受规范活动编号。

必须先备份、恢复演练，并停止 API 和 Celery 写入。迁移先拒绝未知外键、孤立引用及超出安全范围的编号，再暂时移除已审查的入站外键，转换编号并恢复约束。MySQL DDL 不能靠事务整体回滚；失败后保持停写，按备份恢复边界处理，不盲目降级。迁移拒绝破坏性自动 downgrade。

目标为支持实际执行 CHECK 的 MySQL 8.0.16+。CHECK 与外键不使用级联动作，按 [MySQL CHECK 约束说明](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html) 的限制处理。
