## 修复后的行为

| 问题 | 修复结果 |
| --- | --- |
| R1：真实付款取消后失去场地且未退款 | 按首个时段上海时间计算，超过开始前 1 小时可自助取消，真实收款全额退款；恰好 1 小时、1 小时内及开始后拒绝取消。退款确认前保留时段。管理员退款接口支持历史已取消但存在真实收款的订单。 |
| R2：本地取消后成功通知被忽略 | 记录真实交易号并创建全额补偿退款意图；不恢复过期/冲突场地，不确认部分时段。重复成功通知不重复申请退款，交易号冲突拒绝处理。预支付携带本地锁期限，调用前持久化请求日志；响应丢失仍可恢复。每分钟查单/关单任务处理 pending/cancelled 的未完成真实支付尝试。 |
| R3：退款超时后允许新单重复退款 | 管理员退款先提交一条持久化意图与 refunding 快照，然后派发任务；新退款单使用 BR{order_id}，重试复用历史已有单号。相同金额重复请求返回原单，不同金额冲突拒绝；历史多笔记录、关闭或异常退款需人工核对。即时任务派发失败也不丢失申请，周期任务仍能处理。 |
| R4：旧退款误释放新订单时段 | 退款回调、重试和轮询共用同一状态更新；使用订单 → 退款记录 → 时段行锁及 populate_existing，释放时核对 booking_order_id、使用 booking:{order_no} Redis 锁值。失效退款不恢复 paid 或抢回场地；释放异常时回滚数据库状态，下一轮查原单恢复。 |
| R5：取消的待审核报名被恢复 | 比赛审核同时要求 admission=review、status=registered、approval=pending、赛事为 open，旧页面审核已取消报名返回 409。正常审核与候补流程保留。 |
| R6：未确认预约就回传到发布页 | 只有服务端确认 paid 才写 booking_return 并返回活动表单；pending/cancelled/refunding/refunded 均进入预约结果页。订单列表移除“取消并退款”承诺；真实已付款可按一小时规则自助全额退款，异常退款提示管理员核对。 |

退款请求、查询和 SDK 解包在后台线程执行；只有明确 `404 RESOURCE_NOT_EXISTS` 才以原退款号重新提交，查询网络错误或不匹配响应不会当作“退款不存在”。具体的原单重试原则参见 [微信支付退款最佳实践](https://pay.wechatpay.cn/doc/v3/merchant/4014959631)。

退款成功保持终态幂等，错误/关闭通知不能覆盖 success。保留没有本地意图的历史签名退款通知补记路径，要求实际退款金额与订单范围一致。自动分账仍暂缓；自助取消现按负责人明确的一小时规则全退，不启用旧阶梯比例。

一个订场订单本轮只支持一个业务退款意图，包括管理员指定金额的部分退款；不会在同一订单上再新建单号追加部分退款。退款申请受理及 refunding 状态均不等于已经到账。
