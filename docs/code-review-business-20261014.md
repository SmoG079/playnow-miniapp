## 范围与当前实现的差异

`docs/deferred-booking-payments.md` 和 10 月 13 日发布记录描述真实订场支付已注释、开关不能恢复；当前 `backend/app/api/v1/bookings.py:403` 之后已经包含真实预支付分支，前端 `frontend/src/services/payment.ts:54` 也会调起微信收银台。`WX_PAY_ENABLED=false` 仍是占位确认，`true` 则进入真实支付。本次未读取生产环境配置，不能据此断言线上开关或实际收款状态。

真实订场取消退款规则与分账属于已有暂缓范围，本次不把这些功能未实现本身当作新需求。R1、R2 明确说明：当前代码已支持重新开启收款，暂缓代码会如何影响这条实际可达路径。若继续暂缓资金功能，应保持收款入口与暂缓边界一致；恢复真实收款时则需一并完成相应状态恢复与退款验收。

## R1 — P1：真实已付款订场取消后，场地释放但没有退款，也不能通过现有管理员接口退款

位置：`backend/app/api/v1/bookings.py:777-786`；前端 `frontend/src/pages/profile/my-bookings.vue:69`。

触发：订单经真实支付成为 `paid`，用户点击前端“取消并退款”。后端直接把订单改为 `cancelled`、释放全部时段，未创建退款记录或申请退款。管理员退款接口又只接受 `paid`（`bookings.py:828`），因此取消后的该订单无法再通过这个接口补退。用户失去预约，付款仍未退回，且前端承诺与接口结果不一致。

复现：给订单设置非 `dev_` 的真实交易号和 `paid`，调用实际取消函数；结果为 `cancelled`、时段 `available`、退款记录数 0。

建议：暂缓状态下明确限制真实付款订单的自助取消路径和前端退款承诺；如恢复真实取消退款，持久化退款申请及状态后再按确定的政策处理场地释放，并提供取消订单的补偿处理入口。

## R2 — P1：超时取消后收到成功通知，真实收款会被直接忽略

位置：`backend/app/services/payment_callback.py:53-55`；`backend/app/api/v1/bookings.py:471-472`；`backend/app/tasks/tasks.py:26`；`backend/app/api/v1/bookings.py:317`。

触发：微信收款已经发生，但回调/主动查单延迟；锁过期任务或订场时的过期清理先将本地订单改为 `cancelled`。后来的成功通知遇到“非 pending 就返回 SUCCESS”分支，既不记录真实交易号，也不创建异常通知或补偿记录。主动查单同样将 `cancelled` 视为终态，不再查微信。真实预支付调用也没有绑定本地锁的 `time_expire`，本地清理不向微信关单，扩大了本地取消后仍能收款的时间窗口。

复现：创建超过锁 TTL 的订单，先执行 `expire_slot_orders`，再提交金额一致的成功通知；应答 `SUCCESS`，订单仍为 `cancelled`，交易号为空，没有退款记录。

这与此前记录的“pending 状态迟到收款生成异常通知、人工处理”不同：本路径直接丢失收款状态，连异常通知也没有。

建议：将“重复成功通知”与“本地取消后第一次真实成功通知”区分；后者记录真实收款并进入持久化补偿/人工处理状态，不恢复已释放的场地。恢复真实收款时统一微信交易有效期、本地锁期限、查单与关单流程。

## R3 — P1：管理员退款超时后仍保持 paid，重复操作会生成不同退款单

位置：`backend/app/api/v1/bookings.py:841-853,870-883`。

触发：微信退款请求发生网络超时，可能已经被微信受理。异常分支把记录记为 `failed`、提交重试任务并返回 `status=refunding`，但没有把订单从 `paid` 改为 `refunding`，也没有设置订单退款金额/单号快照。用户或管理员刷新后仍看到已支付状态，再次调用退款接口会生成新的 `out_refund_no`。不同单号不能共享微信侧的单号幂等保护。

复现：100 元订单，模拟每次退款响应丢失；连续调用两次 40 元退款，生成 `refund-A`、`refund-B` 两条可重试记录，订单仍为 `paid`，两个 HTTP 调用却均返回 `refunding`。若两笔分别被受理，原本一次 40 元退款可能变成两次 40 元。此处不声称微信会允许累计超过原订单总额。

建议：调用远程接口前持久化唯一退款意图和订单 `refunding` 状态；网络结果未知时查询并复用原单，不新建退款单。若允许多次部分退款，需要显式累计已退/申请中金额并校验可退余额。

## R4 — P1：退款兜底按用户释放时段，会破坏同一用户的新订单

位置：`backend/app/tasks/tasks.py:224-236`（`_update_order_after_refund`）。

触发：旧退款请求尚未完成，旧订单回到/仍为 `paid` 并被取消释放；同一用户重新预订这些时段。旧退款的查单或重试随后返回成功，兜底函数只比较 `locked_by == order.user_id` 就释放时段，没有比较 `booking_order_id`。它虽然查询了其他有效订单，但只在 `booked` 分支使用该保护，`locked` 分支仍错误释放新订单。

复现：旧订单 2 退款中；时段 11、12 已由相同用户的新订单 3 锁定。调用旧订单的退款成功兜底后，新订单仍 `pending`，时段却变成 `available`，`booking_order_id` 还保留为 3。新订单继续支付将无法通过时段状态检查。

此外 Redis 释放值仍用用户 ID，而创建锁值已改为 `booking:{order_no}`，这条任务路径与正常取消/回调路径不一致。

建议：统一调用已有 `release_order_slots`，读取外键明细、加行锁、比较订单归属并使用订单锁值；退款重试和轮询遵循订单 → 退款记录 → 时段的同一锁顺序。

## R5 — P2：用户已取消的待审核比赛报名仍可被批准并恢复参赛

位置：`backend/app/api/v1/tournaments.py:728-734`。

触发：开启报名审核的比赛中，用户提交报名后在审核前取消。取消逻辑设置 `admission=cancelled`、`status=cancelled`，但保留 `approval=pending`。主办方从旧页面或取消记录发起“通过审核”，审核接口只检查 `approval`，随即调用 `admit`，将用户恢复为有效参赛者；付费比赛还会重新生成占位订单。

复现：免费比赛的待审核报名先取消，再由创建者调用实际审核函数；报名由 `cancelled` 变回 `active/confirmed`，无需用户再次报名。

建议：审核只允许当前 `admission=review`、状态有效且赛事仍接受审核的报名；取消/过期后的旧审核请求返回冲突。需要重新参加时由用户重新报名。

## R6 — P2：前端未确认预约成功就回传到活动发布页

位置：`frontend/src/pages/booking/confirm.vue:61-80`。

触发：支付确认轮询返回 `pending` 或 `cancelled`。代码仅改变提示文案，之后仍无条件写入 `booking_return` 并返回约球/比赛表单。约球后端要求关联订单为 `paid`，因此前端把尚未有效预订的场地当作已订回传，发布可能被拒绝；已取消的订单也会进入同一路径。

复现：抽取当前 Vue 文件中的实际 script，使用 TypeScript 转译执行、模拟 uni 与服务依赖。分别令 `confirmBookingPaid` 返回 `pending` 和 `cancelled`，两次都观察到写入 `booking_return` 并返回发布约球页。此验证是脚本流程复现，不是模拟器或真机验收。

建议：仅 `paid` 时回传预约；`pending` 留在结果确认流程，`cancelled` 等终态提供重新订场。前端展示应区分占位确认与真实支付。
