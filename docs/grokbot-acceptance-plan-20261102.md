### SSH 后的检查与访问示例

以下命令在服务器项目根目录执行；使用有权限的账号，按本机配置决定是否加 `sudo`。环境文件仅在服务器使用，不将密码、私钥、Token 或展开后的 Compose 配置贴入群聊。

```bash
cd /home/ubuntu/playnow-miniapp
docker compose --env-file .env.production -f compose.production.yml ps
docker exec club-api python scripts/check_health.py
docker exec -it club-mysql sh -lc 'exec mysql -u"$MYSQL_USER" -p "$MYSQL_DATABASE"'
docker exec club-redis sh -lc 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli PING'
docker exec club-celery-worker celery -A app.tasks.worker inspect ping
docker compose --env-file .env.production -f compose.production.yml logs --tail=100 api celery_worker celery_beat
```

MySQL 的 `-p` 会交互提示输入已有密码。连接后先执行只读确认：

```sql
SELECT DATABASE(), @@hostname, @@version;
SELECT version_num FROM alembic_version;
SELECT id, nickname, role FROM users
WHERE LEFT(openid, LENGTH('qa_acc_20261102')) = 'qa_acc_20261102';
```

前缀使用 `LEFT` 精确比对，避免 SQL `LIKE` 将 `_` 当作通配符。原页面中“8 用户”的实际 openid 命名需用批次清单核对；查不到不能直接重建或删除。Redis 可用 `SCAN` 定位本批次已记录的键，不在共享环境执行 `FLUSHDB` / `FLUSHALL`。本次不提供未认证的公网数据库连接串。

## 3. 登录与数据准备

### 3.1 两条验收线路

- **真实微信 UI 线路**：使用指定 AppID 的真实测试微信账号登录，再由 API 创建和关联测试数据。`qa_acc_*` 是数据库标识，无法让 `wx.login()` 自动切换成这些身份。建议把数据挂到真实测试账号，而不是修改已有用户 openid。真实 openid、手机号只在受控清单中保存。
- **隔离接口线路**：使用独立数据库、独立 Redis 实例、独立上传目录和测试密钥，`DEBUG=true` 才能使用 `dev_` 登录。当前 `auth.py` 同时对开发登录和开发手机号检查 DEBUG；不得为了切号打开生产 DEBUG。接口结果不代替真实微信登录验收。

修改生产 openid 可能与唯一约束、已有报名、资金归属及历史身份冲突，不能作为默认切号方案。原计划的登录选项仍需验收负责人锁定；选定后记录用户、角色与业务数据对应关系。

### 3.2 隔离接口环境运行方式

先准备 Python 3.12 环境并安装 `backend/requirements-test.txt`。通过本机受保护的测试环境配置显式注入以下变量；不要直接读取带远程默认连接的配置启动：

| 配置                                                                        | 隔离环境要求                                                  |
| ------------------------------------------------------------------------- | ------------------------------------------------------- |
| `DATABASE_URL`                                                            | `mysql+asyncmy`，仅连接独立库，名称用 `playnow_e2e_<批次>`，用户仅具备该库权限 |
| `REDIS_URL`                                                               | 独立 Redis；仅更换 DB 编号不能隔离同实例的 Celery 所有行为                  |
| `JWT_SECRET_KEY`                                                          | 独立随机密钥，不复用生产                                            |
| `DEBUG`                                                                   | 接口模拟登录环境为 `true`；生产维持 `false`                           |
| `PUBLIC_BASE_URL`                                                         | `http://127.0.0.1:18080`                                |
| `WX_PAY_ENABLED` / `ACTIVITY_TRANSFER_ENABLED` / `PROFIT_SHARING_ENABLED` | 基础造数均为 `false`，不注入真实商户密钥                                |
| `CLUB_BOOKING_ENABLED`                                                    | 当前产品验收为 `false`；仅历史订场回归进程设置为 `true`                     |
| COS                                                                       | 使用独立测试桶与前缀；没有 COS 时活动图片路径可能返回不可用，不把此项误判通过               |

以下在 `backend/`、已激活虚拟环境且上述变量已注入后执行。仅适用于隔离空库或已有 Alembic 记录的测试库：

```bash
python -m alembic upgrade head
python -m alembic upgrade head
python -m uvicorn app.main:app --host 127.0.0.1 --port 18080
```

另一个终端在同一测试环境中运行：

```bash
cd backend
FULLFLOW_REPORT=/tmp/playnow-fullflow-result.json python tests/http_fullflow.py
```

`http_fullflow.py` 是会写入数据的回归脚本，不是通用生产种子脚本。它校验库名，仅允许 `playnow_e2e_*` / `playnow_migration_*` / `test_db`；API 地址固定为本机 18080。运行其历史场地流程时，API 进程也需设置 `CLUB_BOOKING_ENABLED=true`。脚本会创建管理员并修改数据，需在新建可丢弃库执行，不保证重复执行幂等，也不会自动清空全部数据。完成后重新启动产品配置（订场暂停）的 API，再测暂停行为。

### 3.3 造数顺序与批次台账

优先经 API 创建业务，SQL 仅用于角色准备、时间边界、历史异常和无法通过正常流程形成的测试状态。不要只改状态字段拼装支付、退款、晋级或提现成功记录。

1. 建立 `run_id`（例如 `qa_acc_20261102_r2`），记录目标 API、库、Redis、代码 SHA、迁移版本、开关、造数人和时间。
2. 准备至少 8 个身份：平台管理员、社群 A 群主、社群 B 群主、A 普通成员、非成员、无手机号用户、正常报名用户、并发竞争用户；同一身份可覆盖多个用例，但保留不同用户的越权验证。
3. 创建两个社群，覆盖待审核/通过/拒绝及无场地状态。按审核 API 通过后再创建相关业务，不把普通成员直接当管理员。
4. 创建免费比赛与免费约球，补齐草稿、已发布、满员、已截止、进行中、结束、取消等合法状态。按 API 支持的动作逐步推进；预期不支持的动作记录为范围差异。
5. 创建报名、审核、签到、队伍/对阵、成绩与消息，记录每个业务公开 ID 和关联 ID。使用 API 返回 ID，不硬编码 `16` 或假设公开 ID 等于数据库主键。
6. 特殊付款、退款、24 小时解锁与提现状态放在隔离专项，用 mock 和现有测试夹具构造完整关联。`dev_` 付款不形成真实可提现收入。
7. 保存批次清单：表名、主键、API ID、父对象、文件 key、Redis 键、原值/新增值及清理方式；凭据另存，不随文档分享。

俱乐部 16 只有确认属于该批次且无真实业务依赖后才复用。八个账号不等于八人比赛所有人数边界已覆盖；最小/奇数/满额/超额人数应按当前赛制另建比赛。

## 5. 执行顺序、证据与清理

1. 负责人确认功能补充已落到指定 SHA，核对后端、Worker、Beat 与小程序包版本、迁移及开关；继续保留比赛 A→F 优先级。
2. 锁定真实微信登录方案，先验证 AUTH/ROLE；数据管理员提供批次台账后恢复造数。先跑免费路径，再做隔离资金专项。
3. 比赛 P0 → 约球/社群 P1 → 资料/消息/媒体/分享 → 钱包与暂停策略 → 异常并发 → 真机抽检。资金权限与余额错误可提前阻断放行。
4. 每条用例记录：编号、SHA、环境、run_id、角色、前置对象 ID、步骤、预期/实际、截图/脱敏响应、通过/失败/阻塞/跳过、缺陷等级与负责人、复测结果。接口模拟、开发者工具、真机结果分列。
5. 清理前先停止本批次写入及相关隔离任务，保存脱敏证据并核对外部依赖；按已记录主键反向依赖清理消息/评论、赛程/队伍/报名、活动、社群成员/管理员、社群，最后用户及文件。以实际外键为准。
6. 原页面的“只删除 club_members / clubs / users 前缀”仅适用于没有其它依赖的早期批次；挂上业务后必须扩充回滚清单。真实支付/退款/转账及审计记录不按测试前缀直接删除；已有生产批次不在本次自动回滚。
7. 可丢弃隔离库在确认无生产依赖后整体销毁；共享环境只按精确 ID 清理本批次，验证无孤儿、无残留锁，不用全表删除或 Redis 清空。

放行要求：比赛 A→F 在开发者工具及至少一次真机/体验版抽检通过；约球、社群和其余 P1 主路径通过；所有 P0 资金/权限逻辑通过隔离验证；阻断缺陷清零，剩余缺陷有等级、负责人和处置结论。真实支付、退款、提现未实测的项目需单列，不能宣称真实资金链路已通过；若正式开放相关功能，真实链路验收成为上线前置条件。
